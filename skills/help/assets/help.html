Vibe Engineering Beta

Stop prompting in circles. Start engineering with a plan.

Vibe Engineering gives Claude a methodology for building software, not just generating code. Every feature lives as an item on your GitHub Projects board. Each skill moves it one column forward and writes what it learned into the item, so the next step starts from real context. The result is a well-configured project with a clear architecture and consistent patterns, easy to read, maintain and evolve.

Before the board: create-board makes the board, and create-item puts a new idea in Draft. Review fixes: when a review leaves comments, develop takes the item back to In progress, and push updates the same PR.

Getting started

  1. Log in to GitHub with the project scope. The skills use the GitHub CLI. 
    gh auth login -s project
    Already logged in? Add the scope with gh auth refresh -s project.
  2. Install the plugin in Claude Code. 
    /plugin marketplace add gelonezi/vibe-engineering
/plugin install vibe-engineering@vibe-engineering
  3. Create a board. Ask for one with create-board. It asks where the board goes, from a list of your account, organizations and repositories. An existing board works too, if it has the six columns above.
  4. Name the board every time. Every skill asks which board to use. Give its link, or its name. A skill never picks one for you.
  5. Start with an idea. Say what you want in plain words, and create-item takes it from there.

The rules

These keep the skills predictable. Each one is written into the skills themselves.

One Ready item equals one pull request

promote-ready splits the work until this is true.

The item is the only context

develop reads the item and the repository's own rules, and nothing else. What isn't in the item doesn't exist.

Each skill owns one section

The item text has fixed sections, in order: ## Idea, ## High-level design, ## Spec. A skill writes its own and never edits the others.

Column and content must agree

An item in the wrong column, or missing an earlier section, stops the skill, which says so and asks before continuing.

Set the status last, then check it

Board automations can move items too, so every skill reads the status back and reports any difference.

You always name the board

By link or by name. There is no config file, so nothing can point at the wrong board.

Good to know

Draft column vs. draft issue

create-item makes a GitHub draft issue, because an idea doesn't need a repository yet. promote-backlog turns it into a real issue, which is what a pull request can link to.

You can't approve your own PR

GitHub blocks it. Working solo, review posts plain comments and approve merges without a formal approval. If branch protection requires one, the skill stops and tells you.

Merging can't be undone

approve shows the checks and any unresolved threads, and asks for your confirmation first.

Cloud sessions can't reach boards

On claude.ai, GitHub Projects is out of reach. There create-board sends you to Claude Code on your computer, or guides you through copying the board by hand. The other board skills need your computer for now.

Splitting an item

When one item becomes several, the original stays as the parent and each child is a sub-issue carrying its own copy of the text. The parent closes when the last child is done.

Text accumulates

Every section goes into the same item. GitHub stops at about 65,000 characters, so promote-ready warns before reaching it.
